RoseMCP's windows, redesigned from the use cases

You asked for the use cases first, then a design built on them, with the current windows treated as disposable. This page starts from the use-case catalogue and your answers to it. It sets out the requirements as they now stand, then the windows that meet them, then what Rose needs underneath and the order to build it in.

This file is the design tier 5's cards work from; the cards themselves are in 00-overview.md. It was drafted and reviewed as a claude.ai page, and the use-case catalogue it links to is a private page there. The mock-ups use example data: the app, its code, the agents and the timings are made up. Where Rose can't do something today, the page says what it takes, checked against RoseMCP main at cc977f3 and the Claude Code docs.

What your answers changed

  • The windows are organised by agent. The first thing you see is each agent session and what it's doing against which workspace. Workspaces come second.
  • Warnings written for the agent shrink to one line. You can open the full detail, and you can accept a known one, such as the HintPath test projects, so it stops drawing attention.
  • You can talk to the agent from wherever you're looking. Select a value, a frame, a thread, an element, a measurement or a colour, write a note, and Rose gets it to the agent. No copy-paste.
  • You can debug without an agent. Open the debugger from the tray, attach to or launch an app yourself, and bring an agent in when you want one.
  • Rose knows its own build. It shows the commit, whether the tree was dirty, and whether each agent's connection still matches. A restart only touches agents whose tools actually changed.
  • Kept quiet. No window at start-up. Notifications only for things you can act on.

Six principles the design follows

Each one comes from an answer above. When two screens disagree, these decide.

Quiet until it needs you

The tray icon carries Rose's state. A window opens only when you ask. A notification only comes for something you can act on: a new release, Rose failing, or an agent answering you.

Organised by agent

The first view is the agent sessions: what each is doing, against which workspace and which app. Workspaces and apps are views of their own, linked both ways.

One line for what the agent was told

A warning written for the agent takes one line in the window, and the detail is a click away. Strong colour means you can do something about it.

Talk to the agent where you're looking

Anything you can select, you can send to an agent with a note. Rose delivers it and shows you when it arrived.

You can do what an agent can

Attach, launch, break, step and inspect without an agent. Bring one in when you want it.

Rose knows its own build

Every process and every agent connection knows which commit it runs and whether its tools match. A restart touches only what changed.

The tray icon

The tray process hosts the broker and the icon, and no window. Clicking the icon opens the Rose window, in a separate process (decided, question 1).

The Rose window: agents first

Opened from the icon. The left rail picks the view. Agents is the default, because it answers what you said you want to see.

  • A status bar runs along the bottom of every view. It shows Rose's own memory, split into the broker, the workers and the live-app hosts. The apps being debugged are listed separately, so your app's memory doesn't read as Rose's cost. The machine's total sits at the right.
  • Operations is one list with no separate "now". Running operations sit at the top. Finished ones follow, newest first by when they finished, then by when they started. The time column shows when each finished (or, for a running one, when it started), and the duration is always in the right-hand column, counting up while it runs.
  • Two sessions in one folder are two cards. Each is a relay process, so Rose can tell them apart, and they share the workspace card. Subagents behind one session stay one card, as before (#410).
  • "All on this build" changes to "1 session is using tools from before the restart" when a client didn't refresh. Only an HTTP client without the relay can end up there.
  • Each workspace and app chip links to its own view, and those views link back to the agents using them.
  • The Rose window's own reads never count as activity, so opening it can't push the agents' calls out of view the way the Inspector's polling does today.

Workspaces: one line of health, detail on request

The machine view: what's loaded, for whom, what it costs, and whether its answers can be trusted. The example is the Drawboard.All.slnx case you described.

  • Each folder opens in Explorer from its row, and from the detail's Open folder button. Configuration and Platform show what Rose loaded the solution with, so the drawer no longer needs a note about which configuration was chosen.
  • Accepting is remembered per solution, per kind of reason, per project, across loads. A new kind of warning, or a new project that fails, still shows.
  • When you accept a warning, you choose what agents read about it: Rose's own line, a note of your own, or nothing. "What agents are told" shows the exact text (question 4).
  • "Ask an agent why" sends a note about that warning to an agent using the workspace, by the same route as Ask in the debugger.
  • An agent can acknowledge a warning so it isn't repeated on every read for its session. It can also propose accepting it, which shows here for you to confirm. An agent's acknowledgement lasts only for its own session; anything longer goes through you.
  • A rebuilt analyzer, generator or code-fix DLL is spotted by a cheap file check on the next read. With the setting on, Rose reloads the workspace once nobody has used it for a minute.

Activity: every call, by agent, kept

Where you go after something went wrong. It holds every call into Rose with who made it, where, and how it ended. It survives reloads and restarts, and is kept for 7 days.

Debug an app, with or without an agent

The debugger opens from the tray menu, the Rose window, or an agent's session. Opened on its own, it starts here.

The debugger: one view of the app, the agent, and you

The tabs are gone. Threads and stack sit on the left, source and values in the middle, and a single stream on the right holds the app's events, the agent's calls and your notes. XAML is the second view of the same session. It keeps the Inspector's name and icon.

  • Ask an agent works on every row you can select: a local, an argument, a watch, a frame, a thread, an event or exception, a breakpoint, an element or property in the XAML view, and a call in Activity. It also has a keyboard shortcut. The note carries a structured reference (session, thread, frame, value path) and a readable line, so the agent can look the thing up instead of trusting a copied value.
  • "Arrives now" appears when the agent's session listens for Rose, through a Claude Code channel. Otherwise it reads "Arrives with its next Rose call", and the note is attached to whatever the agent calls next, live-app or not. Either way the stream shows when it arrived.
  • The reply in the stream comes from a small tool the agent can call to answer you. That matters most for headless sessions, where nobody reads the terminal. In an interactive session, the agent may just answer in the terminal.
  • The execution buttons use the standard debugger glyphs. Hovering one shows its name and the usual shortcut: Continue F5, Step into F11, Step over F10, Step out Shift+F11. Detach is the unplug icon. Pause is greyed out while the app is stopped.
  • Hold stays a word, next to the countdown it cancels. No standard glyph means "keep it stopped until I continue", and an icon would be read as Pause.
  • The data's age shows next to Live, for example "host last answered 14 s ago" when the host stops answering.
  • When the app exits, the header says so and names the session's log, and the window stays open until you close it.

XAML and the in-app panel: see what the agent changed, and answer it

The debugger's XAML view and the panel show the same thing from both sides: the tree with properties, and the app itself. Both can mark the agent's recent live edits, each with its own switch.

  • Changes fade from the app after 10 minutes, or when you switch them off. The tree keeps its marks for the whole session.
  • A ruler measurement can be pinned with a click, so it stays still long enough to send: "the gap between the Eraser button and the Width slider is 14 px, should be 8".
  • The panel keeps its rules: it takes no input from the app, and only a person arms select mode.

What Rose needs underneath

The windows are the visible part. Most of the work is in the broker, the relay and the operator API, and each item below is something one or more use cases can't do without.

U1Build identity

  • Stamp each assembly at build time with its full commit (the SDK already adds it), whether the tree was dirty, the build time, and, for a local build, the checkout it came from.
  • Show the commit to people. Handshakes compare the commit, not the version, because today two local builds with the same version can't be told apart.
  • A hello route on /operator returns all of it.
  • For a local build, Rose reads the checkout's HEAD and origin/main to say how far it has moved on.
Serves A2, A8

U2A relay that outlives a deploy

  • Today a deploy kills every relay started from the install folder, so each session needs /mcp. Install the relay where the deploy doesn't replace it, and version its own protocol, so only a relay change stops relays.
  • On reconnect, the relay compares a hash of the tool definitions and server instructions. If they're the same, it carries on. If not, it sends tools/list_changed. Claude Code's MCP docs say it fetches the new list without a reconnect; older versions needed one. The relay must advertise listChanged in its own initialize response, because Claude Code only talks to the relay.
  • The first result after a restart says what happened: "Rose restarted on d41a9e0; loaded solutions reload on first use; your debug session ended".
Serves A9, A2

U3Who's connected

  • At connect, the relay tells the broker who it serves: the session's roots (Claude Code answers roots/list with its working folders), the branch, the Claude Code process, and an optional ROSE_AGENT_LABEL, which whatever starts a session can set, for example to the task it was given.
  • The broker keeps a table of clients. An HTTP client without the relay shows up as unnamed.
Serves A3, B4

U4The activity record

  • Every call is recorded with its client, its workspace or debug session, the tool, the target, when it started and finished, the outcome and the error, and its arguments and response.
  • For an edit, the record keeps each changed file's diff, taken from the document before and after. A very large response is cut to a set size, with a note saying so.
  • It's written to disk and kept 7 days, so it survives reloads and restarts.
  • The windows' own reads aren't activity.
  • This replaces today's eight unattributed calls per workspace, forgotten on close.
Serves B3, B4, C3

U5Notes to an agent

  • A route takes a note: to whom, about what (structured), and your text. The broker queues it per client.
  • Always: it's attached to that client's next Rose call of any kind, using the notices mechanism results already have.
  • When the session listens (a stretch goal): it's pushed at once as a Claude Code channel message through the relay. During the preview, that takes an interactive session started with the development-channels flag, or Rose installed as a plugin. Headless sessions get notes on the next call.
  • An optional rose_reply tool lets the agent answer into the window.
Serves C8, D8, D1

U6Debug sessions you start

  • Operator routes to list running .NET apps with windows and installed packages, and to attach and launch.
  • The attach rules and the clean-up after a failed start move from the agent tool into the session manager, where both routes share them.
  • A session's owner becomes a set: you, plus any agent session you share it with. rose_debug_list shows a shared session to that agent.
  • Two decision records change: "the inspector is always a client of a session some agent started" no longer holds.
Serves E5, E6

U7A record of live edits

  • Each rose_xaml_apply change is kept for the session: when, by which client, the element's handle, the property, old and new value.
  • The tap's existing outline-and-badge drawing marks the elements, and the XAML view reads the same list.
  • Today an edit's result goes once, to the caller, and nothing else remembers it.
Serves D2

U8Workspace health with a shape

  • Today's reasons are plain strings. Give each a kind, an effect (blocks answers, may affect some projects, or a note), the projects it covers, and when it was first seen.
  • An accepted reason is remembered per solution, kind and project.
  • Each accepted reason stores what agents read about it: Rose's line, your note, or nothing.
  • A tool lets an agent acknowledge a reason for its own session, or propose accepting it for you to confirm.
Serves B1

U9Spot a rebuilt analyzer

  • At load, record each analyzer reference's path, write time and length. Check them in the read barrier, which already checks files.
  • On a change, tell the agent and the window, and optionally reload when idle. A reload starts a new worker; an assembly can't be unloaded in place.
  • This doesn't depend on the windows and can ship first.
Serves B5

U10Everything through the operator API

  • The tray window reads the broker's objects directly today. The Rose window reads only /operator: clients, workspaces, activity, notes, sessions.
  • That lets it run in its own process and start on demand. Tests can drive it, and so can the later Rose-driven UI automation.
  • The tray process keeps no window, which fixes the window opening at start-up for good.
Serves A1, F1 later

Decisions for you

Each has the answer I'd pick and why. Everything else on this page follows from your answers to the catalogue.

  1. Move the windows out of the tray process into one Rose app, started on demand? Decided: yes, 11 Oct The reasoning that put the Inspector in its own process applies to the main window too: a window crash shouldn't take the broker and every agent's workspace with it. It also gives one codebase for both windows and fixes the start-up window for good. The cost is that the window reads everything through /operator, which it needs for testing and UI automation anyway. With the app closed, the tray icon and its notifications carry a note's delivery and any reply on their own.
  2. Make the stdio relay the standard way to connect? Decided: yes, 11 Oct It's largely how sessions connect already. Only the relay can say which session it serves, reconnect by itself after a deploy, and carry a channel push. A direct HTTP connection keeps working, but shows up as unnamed and gets notes only on its next call.
  3. Do you want notes pushed into interactive sessions? Decided: next call first, push as a stretch goal, 11 Oct During the preview, a push needs Claude Code started with --dangerously-load-development-channels server:rose, or Rose installed as a plugin. If Drawboard's Claude account is Team or Enterprise, an admin must also turn channels on. Without that, notes arrive with the agent's next Rose call, which works everywhere, including headless sessions. So next-call delivery is the baseline. Packaging Rose as a Claude Code plugin is the cleaner route to push, and it would also make setup a single install.
  4. Should accepting a warning also stop the agent being told? Decided: your call per warning, 11 Oct When you accept one, you choose what agents read about it: Rose's line, your own note, or nothing. You can ask an agent why it happens. An agent can acknowledge a warning for its own session, or propose accepting it for you to confirm. The Workspaces section shows it.
  5. Close tier 5's old cards as superseded? Decided: yes, 11 Oct This redesign becomes tier 5 of Fable Review 2, the next work in the milestone, not a milestone of its own. #388–#392 close as superseded by the cards above. #393, the magnifier's reason, stays: the magnifier isn't going anywhere. #226 (card 27) joins 5.13.
  6. A2: is my reading right? Decided: yes, 11 Oct When the tool definitions match, the agent's connection carries on and Claude Code never hears about the deploy. When they differ, Rose refreshes the agent's tool list. The broker still restarts on every deploy, because the code behind the tools changes even when the list doesn't.

Still open, with the default the cards use

  • Keep workers and live-app hosts across a deploy when their build hasn't changed? That would need named pipes in place of stdio, children that outlive the broker, and adoption by the new broker. It's not in tier 5 unless you add it.
  • Does an agent's acknowledgement of a warning carry across sessions? Default: it lasts for the agent's own session; anything longer goes through you.
  • Should the build move from the left rail into the memory bar? Default: it stays in the rail.
